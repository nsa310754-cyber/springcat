# Bionic Runner

Android (bionic libc) 向けにビルドされた ELF 実行ファイルを root 権限で実行し、
APK もインストールできるアプリ。

ビルド済み APK: `dist/BionicRunner-1.29.0.apk.part0`・`.part1` (すべての CPU 用が入ったもの。112MB あり GitHub の上限を超えるので 2 つに分けてある。つなげ方は [`dist/BionicRunner-1.29.0.README.txt`](dist/BionicRunner-1.29.0.README.txt))

## できること

- **パソコン風のホーム画面** — 端末のホームアプリに設定できるデスクトップ。登録した実行ファイルが
  アイコンとして並び、タップするとターミナルで実行される (長押しで引数付き実行・削除)。
  アイコンは長押ししたまま動かすと並べ替えられ、別のアイコンに重ねるとフォルダになる
  (フォルダにさらに重ねると中に入る)。フォルダはタップで開き、長押しで名前の変更・解除、
  中のアイコンの長押しで「フォルダから出す」。中身が 1 個になったフォルダは自動で解除される。
  並びとフォルダ分けは保存され、次に開いたときもそのまま。
  タスクバーの「☑ 選択」(またはフォルダの長押し →「複数選択」) で **複数選択** ができる。
  タップで選ぶ / 外し、下の帯の「すべて選択」「📁 フォルダにまとめる」「🗑 アンインストール」で
  まとめて操作する (選んだフォルダは中身ごと)。アンインストールは、登録したプログラムはそのまま削除、
  Android アプリは Android の確認画面を 1 つずつ出し、ショートカットはホーム画面から外す。
  組み込みの機能は消さない。「✕ やめる」か戻るボタンで選択を終える。
  - **ホーム画面の表示の切り替え** — タスクバーの「表示: …」で、並べるものを 4 つから選ぶ:
    「全部」(組み込みの機能・登録したプログラム・端末の Android アプリ・Chrome の「ホーム画面に追加」で
    置いたショートカット)、「APK・AAB・PWA のみ」(Android アプリとショートカット)、「bionic・glibc のみ」
    (登録した実行ファイル。ほかの CPU 用でエミュレータで動かすものも含む)、「その他のみ」(sh などの
    スクリプト・tar.gz などから展開したもの)。並びとフォルダ分けは表示ごとに別に覚える。
    組み込みの機能は「全部」のときだけ並ぶ (ほかの表示ではタスクバーから開く)。
  - **Chrome の「ホーム画面に追加」** — Bionic Runner をホームアプリにしていると、Chrome などがホーム画面に
    ショートカットを置くときに確認が出て、「追加」でホーム画面に並ぶ (Android 8 以降)。PWA を
    インストールしたもの (WebAPK) は Android アプリとして並ぶ。
  - **アイコンの情報** — アイコンを長押しして (動かさずに) 離すと、アプリ情報が出る。
    種類 (APK / AAB から入れた分割 APK / PWA / ショートカット / bionic / glibc / 静的リンク /
    ほかの CPU 用 / スクリプトの言語 / 圧縮ファイルから展開)、版・大きさ・入手元・CPU・ローダなどの詳しい情報、
    セーブデータ (Android アプリは root で大きさの表示・Download へのバックアップ・消去。登録したプログラムは
    ~/.名前・~/.config/名前 などの保存場所の表示・バックアップ・消去・エクスプローラーで開く)、
    アンインストール (ショートカットは「ホーム画面から外す」)、その他 (実行・強制停止・APK の取り出し・
    Play ストア・ウイルス検査・アイコンの変更など)。
  元から入っている Android アプリは、タスクバーの「スタート」から検索して起動する
  (長押しでアプリ情報)。ホームアプリの切り替えはスタートメニュー下部の「ホームアプリの設定」から。

- **実行ファイルの実行** — ファイルを選ぶとヘッダを読み、bionic 動的リンク / 静的リンク /
  glibc 動的リンク / Windows の .exe / スクリプトを判定して表示。
  登録するとアプリ内の `bin` に置かれ、以後はコマンド名だけで呼び出せる。
- **圧縮ファイルの実行** — 「実行ファイル」から tar.gz (tgz)・tar・tar.xz・tar.bz2・zip を選ぶと、
  展開して中の実行ファイル (ELF とスクリプト) を探す。1 個ならそのまま、複数あれば選んで登録する。
  同梱のデータを読めるよう、展開した一式は `pkg/<登録名>` にまとめて置き、既定では
  そのフォルダの中で実行する (登録時のチェックで切り替え)。圧縮しただけの 1 個のファイル
  (`prog.gz` など) も、取り出して実行できる。検知は展開した全ファイルに対して行う。
  展開先の外へ書き出そうとする項目 (`../`、外を指すリンク) は取り出さない。
  複数あるときは、選ぶ画面のいちばん上の「★ すべて登録」で、中の実行ファイルを全部それぞれの
  コマンド名 (ファイル名。同じ名前は `-2` などを付ける) で登録できる。中身は 1 個目の登録名の
  `pkg/<登録名>` に 1 つだけ置き、ほかの登録名の `pkg/<登録名>/root` はそこへのリンクにして共有する。
  登録するだけで、全部を一度に起動はしない (補助のプログラムまで動いて重くなるため)。
  共有元の登録を消しても、中身は残りの登録へ引き継ぐので、ほかのコマンドは動き続ける。
  ホーム画面では、まとめて登録したアイコンを 1 つのフォルダ (名前は圧縮ファイルの名前) に入れる
  (表示の切り替えごとに、次に開いたときにまとめる)。1.35.0 で登録したものも、1 回だけまとめる。
  xz と bzip2 は端末の `xzcat` / `bzcat` を使うので、それが無い古い端末では展開できない。
  7z・rar・zstd には対応していない。root が無い場合、展開した中のスクリプトが同梱の別の
  プログラムを直接呼び出すものは動かない (Android がデータ領域のファイルの実行を禁じているため)。
- **アップデート** — 実行ファイルや圧縮ファイルを開いたとき、同じアプリがもう登録されていれば
  「アップデート」として扱い、同じ登録名で中身を置き換える (デスクトップでの位置やフォルダ、
  アイコンはそのまま)。名前が版の番号や CPU の種類で少し違っていても (`game-1.2.exe` と
  `game-1.3-arm64.exe` など) 同じアプリとして見つける。別のアプリとして残したいときは登録名を変える。
  中身がまったく同じなら置き換えず、登録済みのものをそのまま実行できる。
- **アイコン** — 登録したプログラムにアイコンがあれば、デスクトップに頭文字の代わりに表示する。
  圧縮ファイルから登録したときは、中のアイコンらしい画像 (`icon.png`・`.DirIcon`・`.desktop` の
  `Icon=` が指す画像・実行ファイルと同じ名前の画像・`.ico`) を使う。Windows のインストーラーや
  自己解凍形式の exe から登録したときは、exe に埋め込まれたアイコンを取り出す。
  デスクトップで長押し →「アイコンを変更」で好きな画像にもできる。
- **glibc 用プログラムの実行** — 一般の Linux 向け (glibc 動的リンク) の ELF も、同梱の
  glibc 2.41 + libstdc++ (GCC 14) で起動する。初回に端末の CPU 用の一式を展開する。
- **絵や音を出すプログラム (ゲーム)** — SDL2 を使う glibc 用プログラムは、ウィンドウの中身が
  アプリのゲーム画面に表示され、音が端末から出る。タッチはマウス操作、画面上のボタン
  (矢印・Z・X・Space・Enter・Esc) と画面キーボードはキー入力として届く。
- **32bit の ARM 用プログラム (armeabi / armeabi-v7a)** — 64bit 専用の端末 (対応 CPU が arm64-v8a
  だけの最近の機種) では OS が 32bit のプログラムを実行できないので、同梱の CPU エミュレータ
  (QEMU のユーザーモード `qemu-arm`。Termux の Android 用ビルド) を挟んで動かす。直接より遅い。
  動かせるのは静的リンクの ELF と、glibc を動的リンクした ELF (同梱の 32bit 用 glibc を使う)。
  32bit の Android 用 (bionic 動的リンク) は、端末に 32bit 版のシステムライブラリが無いので動かない
  (その旨を表示する)。エミュレータは `fetch-qemu.sh` で取得する (リポジトリには入れていない)。
- **PC 用 (x86_64) の Linux のプログラム** — ARM の端末でも、同梱の CPU エミュレータ
  (`qemu-x86_64`。32bit ARM 用と同じく Termux の Android 用ビルド) を挟んで動かす。
  動かせるのは静的リンクの ELF と、glibc を動的リンクした ELF (同梱の x86_64 用 glibc を使う)。
  x86_64 の Android 用 (bionic) は動かない。32bit の x86 (i386) 用には対応していない。
- **Box64 (x86_64 を速く動かす)** — x86_64 の Linux のプログラムは、Box64 (x86_64 の命令を ARM64 の命令に
  変換しながら動かす仕組み。MIT ライセンス) が入っていれば、QEMU より速い Box64 で動かす。下の Wine の
  土台でもある。
  - **入れ方**: ビルドの前に `./fetch-box64.sh` を実行する (Termux の termux-pacman の glibc 系の配布物
    `box64-glibc` の arm64 版を取る)。版は動作を確かめたもの (0.4.4-0) に固定してあり、スクリプトに書いた
    SHA-256 で照合する (ビルドする日によって中身が変わらないように)。`BOX64_LATEST=1 ./fetch-box64.sh` で、
    配布元の一覧からその時点の最新版を取る (一覧の SHA-256 で照合)。取った版は `assets/box64/VERSIONS.txt`。
    本体は `jniLibs/arm64-v8a/libbox64.so` (デバッグ用の情報を外して約 35MB)、x86_64 用の補助ライブラリ・
    設定ファイル・ライセンス・動作確認用の小さなプログラムは `assets/box64/arm64-v8a.zip`。
    リポジトリには入れない。実行しなくてもビルドはでき、そのときは今までどおり QEMU で動く。
  - **しくみ**: Termux 版の Box64 は glibc の arm64 用プログラムなので、アプリ同梱の arm64 用 glibc の上で
    動かす。x86_64 のプログラムが使うライブラリは、同梱の x86_64 用 glibc (`assets/glibc/x86_64.zip`)
    と Box64 付属の補助ライブラリを `BOX64_LD_LIBRARY_PATH` で渡す (`BOX64_PATH` は PATH と同じ)。
  - **切り替え**: 設定 → 個人設定 →「x86_64 の実行方法」で 自動 / Box64 / QEMU を選ぶ。どれで動かすかは
    実行のたびに起動スクリプトの中で決めるので、登録済みのプログラムにもすぐ効く。1 回だけ変えるときは
    `BR_X86=qemu 名前.Gelf` のように環境変数で指定する。
  - **動かないとき**: 初めて x86_64 のプログラムを実行するとき (とアプリの更新後) に、小さな x86_64 の
    プログラムを Box64 で動かして、この端末で動くか確かめる。動かなければ (ページサイズが 16KB の端末
    など)、自動で QEMU に切り替えて「Box64 が使えないため QEMU で実行します (理由)」と 1 行出す。
    たまたまの失敗 (メモリ不足など) で決めつけないよう、次の実行でもう 1 回だけ確かめ、2 回続けて
    失敗したときだけ「この端末では動かない」と記録して、以後は QEMU で動かす。
    設定の「Box64 が動くか、次の実行でもう一度確かめる」でやり直せる。
  - **制限**: 64bit の ARM 端末だけ。32bit の x86 (i386) などは QEMU のまま (Box64 の i386 対応版は入れていない)。
    圧縮ファイルから展開した一式の中の x86_64 のプログラムは、登録し直すまで QEMU のまま。
    Box64 は、プログラムが使うライブラリのうち対応しているもの (libc など) を ARM 用の本物に置き換えて
    速くするので、プログラムによっては動かないことがある (そのときは設定で QEMU を選ぶ)。
    APK が約 30MB 大きくなる。
  - **速度を比べる**: 設定 → 個人設定 →「速度を比べる (ネイティブ・Box64・QEMU)」で、同梱のベンチマーク
    (`bench4`) を動かし、1. 整数の計算とループ (割り算なし) 2. メモリの読み書き 3. libc の関数
    4. 起動の速さ (50 回) の時間を、ネイティブ (同じソースを mkexe の tcc で arm64 向けにビルド)・Box64・QEMU
    で並べた表にする。サンプルの元は [`samples/x86_64-glibc`](samples/x86_64-glibc) (`bench4.c`・`bench.sh`)。
- **Windows のプログラム (Wine)** — 64bit の Windows のプログラム (x86_64 の PE / .exe) を、Box64 の上の
  Wine で動かす。ウィンドウは X11 の画面 (Xvnc) に出る。
  - **入れ方**: X11 の画面の「追加機能」(コマンドなら `x11 addons`) のいちばん上の
    「Windows のプログラム (Wine)」で「ダウンロード」。大きいのでアプリには同梱せず、この画面を閉じても
    最後まで続く。取ってくるのは **Debian 13 (trixie) の公式の配布物** (`deb.debian.org`) の
    `wine64`・`libwine`・`fonts-wine` (Wine 10.0~repack-6) と `libz-mingw-w64`、Wine が使う x86_64 用の
    ライブラリ (libX11・FreeType・fontconfig など 22 個) の合わせて 26 個 (約 110MB、入れたあと約 750MB)。
    fontconfig (字体の設定) は 1.30.15 で足した (無いと Wine 10.0 は画面まわりの初期化の途中で、読み込めなかった
    fontconfig の関数を呼んで落ち、ウィンドウステーションが作られずに止まる)。それより前に入れた Wine には、
    「追加機能」の「更新」で、足りない 2 個 (約 0.5MB) だけを足す。
    版を固定し、各パッケージの SHA-256 を `Wine.java` に書いてあり、ダウンロードのたびに照合して、
    合わないものは使わない (表の値は、Debian の鍵で署名された一覧 (Release → Packages) から写した)。
    Box64 が無い APK (`fetch-box64.sh` を実行せずにビルドしたもの) や 64bit の ARM 以外の端末では、
    「Wine は使えません」と出る。
  - **使い方**:
    - 「実行ファイル」で .exe を選ぶと、ほかのプログラムと同じ登録の画面 (検査の結果・登録名・引数・
      「登録して実行」「登録のみ」) が出る。登録すると、本体を `files/wine/programs/` に置き、デスクトップの
      アイコンやコマンド名から Wine で動かせる。動かせないもの (ARM64 用の exe や、32bit の部品を入れていない
      ときの 32bit の exe) は、理由だけを出す。
    - エクスプローラーで .exe を長押し →「Wine で実行」。登録と同じ検査をしてから、コマンドプロンプトに
      `wine ファイル` が送られ、出力はそこに出る。危険な記述が見つかったときは内容を見せ、
      「それでも実行」を選んだときだけ動かす。
    - 検査 (危険な操作の記述を探す) には、Windows 向けの項目もある: 復元用の記録 (シャドウコピー・バックアップ)
      の削除、起動・回復の設定の書き換え、ドライブの初期化・完全消去、Windows Defender の無効化、
      PowerShell・certutil などで外から取ってきて実行、イベントログの消去、ブラウザのパスワードや暗号資産の
      ウォレットの読み取り。Windows のプログラムが UTF-16 で持つ文字列も調べる
      (Wine 付属の 752 個のプログラムで、誤って危険と判定するものが無いことを確かめた)。
    - コマンドプロンプトで `wine プログラム.exe 引数…`。例: `wine cmd /c echo hello`、`wine notepad`、
      `wine winecfg`。`wine --stop` で、動いている Windows のプログラムをすべて止める。
      `wine --reset` で Windows の環境 (C: ドライブ) を消して作り直す。
      `wine --diag` で、動かないときの原因の手がかり (利用者・カーネル・ページサイズ・フォルダの状態・
      Wine と Box64 の詳しい記録) を `Download/wine-diag.txt` に保存する (保存するだけで、どこにも送らない)。
    - ウィンドウを出すプログラム (exe の中の印で判断する) のときは、X サーバーを **裏で** 起動して
      (画面はまだ切り替えない)、準備ができるのを待ってから動かす。X11 の画面に切り替えるのは、プログラムの
      ウィンドウが本当に出てから (`libbrxwin.so` (`native/brxwin.c`): X サーバーに、起動したときに無かった
      普通のウィンドウが出るまで待つ小さな道具。X11 の決まりのうち接続・QueryTree・GetWindowAttributes だけを
      自分で話し、画面の中身は読まない)。それまではコマンドプロンプトに経過やエラーが出たままなので、
      ウィンドウを出さずに終わったり落ちたりしたときも、そこで分かる (「ウィンドウを出さずに終わりました」と出す)。
      先に X11 の画面を見るときは `x11` と入力する。Linux 環境や X サーバーがまだ入っていない (初回の準備が要る)
      ときだけは、最初から X11 の画面を開く。
    - 初めて動かすときに Windows の環境 (`files/wine/prefix`、WINEPREFIX) を作る (1〜数分。途中の経過を出す)。
      Wine 付属の DLL は、同じ中身のコピーの代わりに本体へのリンクにして、約 700MB を約 20MB にしている
      (Wine が環境を更新するときにリンクの先を書き換えて壊さないよう、本体は書き込み禁止にしてある)。
      作るのに失敗したとき (kernel32.dll ができていないとき) は Wine の記録の最後を出し、次の実行で作り直す。
    - 環境変数は `WINEDEBUG=-all`、`WINEDLLOVERRIDES=winemenubuilder.exe=d;mscoree=d;mshtml=d` (Linux のメニューや
      ファイルの関連付けを作らせない。.NET (Mono) とブラウザ部品 (Gecko) を入れようとしない)、`LC_ALL=C.UTF-8`、
      `DISPLAY=:1`。スマホのメモリで足りるよう、Wine に見せる CPU の数は 4 にする (Box64 の設定では 64)。
      Windows の環境づくりは優先度を下げて動かし、5 秒ごとにメモリの様子を記録する
      (`wine --log` で `Download/wine-log.txt` に保存。メモリ不足でアプリごと止められたときに調べるため)。
      環境づくりの間はデスクトップ (explorer.exe) を起動させない (スマホでは explorer が起動に失敗し続け、
      プログラムが動くたびに起動し直してメモリを使い切っていた)。
      安全装置: 空きメモリが 250MB を切った状態が 2 回 (約 4 秒) 続いたら、Windows のプログラムをすべて止めて
      理由を出す (端末が固まったり、アプリごと止められたりしないように)。
  - **ドライブの割り当て (安全のため)**: Wine のふつうの設定では Z: ドライブが `/` (端末全体) になる。
    これを作らず、ドライブは **C: (Windows の環境)・D: (共有フォルダ `files/wine/shared`)・
    P: (登録した Windows のプログラムの置き場所 `files/wine/programs`)** と、動かす exe のフォルダを指す **E:** だけにする。
    Windows のプログラムとファイルを受け渡すときは D: (エクスプローラーの「アプリの作業領域」→ wine → shared)
    を使う。Z: は毎回確かめて、作られていれば消す (winecfg で足しても次の実行で消える)。
    動かす exe は、Windows の場所 (ドライブ名付き) で Wine に渡す (どのドライブにも無い場所のままだと、Wine が
    見つけられず「ShellExecuteEx が失敗: ファイルが見つかりません」になる。1.40.0 までは、登録した exe がこれで
    動かなかった)。C: / D: / P: の中ならそのドライブで、それ以外の場所 (`wine /sdcard/Download/x.exe` など) なら、
    その exe のフォルダを E: にして渡す (E: は動かすたびに付け替える。別の場所の exe を 2 つ同時に動かすと、
    先のほうから E: が見えなくなる)。

    コマンドはアプリに合図を送り、アプリ自身 (普通の権限) が動かして、出力をコマンドプロンプトに出す
    (`su アプリの番号` で戻すだけだと、作ったファイルの SELinux の印が普通のアプリと違ってしまい、あとで
    普通のモードから消したり書き換えたりできなくなるため。このとき Windows のプログラムへの文字の入力はできない)。
    wine.sh 自体も root では動かない。1.30.1 以前に root モードで動かして消せないファイルが残ったときは、
    root モードで `wine --reset` (Windows の環境を消す。D: の中身は残す)。初めて Windows の
    プログラムを動かすときに「Windows のプログラムはアプリの権限で動きます。信頼できないものは動かさないで
    ください」と 1 回だけ確かめる。

    `wine64` を動かす。Box64 が自分を起動し直すとき (wine64 が wineserver を起動するときなど) のために、
    `fetch-box64.sh` が libbox64.so に書かれたローダの場所を `files/box64/ld` に書き換え、アプリがそこから
    同梱の `libbox64ld.so` (`native/box64ld.c`。アプリと同じ形 (libbrld.so + 補助ライブラリ) で Box64 を
    起動し直すだけの小さなプログラム) へのリンクを作る。
    Debian の Wine は、wineserver との連絡用のフォルダを `/run/user/番号` か `/tmp` に作るが、Android には
    どちらも無い。環境変数 TMPDIR で変える仕組みは Debian の変更 (`temporary-directory.patch`) の不具合で
    強制終了するので使えない。そこで、入れるときに `ntdll.so` と `wineserver64` の中の「/run/user」を使う
    1 か所だけを、アプリのフォルダ (`files/wine/run`) を指すように書き換える (`WinePatch.java`)。
    また `win32u.so` の、画面まわりの初期化 (init_user: 描画・設定・ウィンドウステーションの準備) を
    `pthread_once` 経由で呼ぶ 1 か所を、直接呼ぶように書き換える (call 命令の行き先 4 バイト)。
    Box64 の pthread_once は、同じ初期化が実行中だと 10 ミリ秒で待つのをやめて「終わった」とみなすので、
    スマホでは初期化が行われないまま進み、ウィンドウステーション (WinSta0) が作られずに止まっていたため
    (この関数はプログラムごとに 1 回しか呼ばれないので、直接呼んでも同じ)。入れ済みの Wine には、
    アプリの起動時に同じ書き換えをする。
    ほかに、wineserver を起動する Debian 用のスクリプトを本体へのリンクに置き換え、`zlib1.dll` を
    Windows の環境に置く。

- **「inaccessible or not found」の対策** — Android のシェルは、コマンドが見つからないときも実行できない
  ときも同じこの文言を出すので、原因が分からない。そこで:
  - 登録するスクリプトを Android で動く形に直す: 1 行目の `#!/bin/bash`・`#!/usr/bin/env python3` などを
    端末にある処理系 (`/system/bin/sh`・同梱の python3・lua) に置き換え、Windows の改行 (CR LF) を直す。
  - 同梱のコマンド (`bash`・`curl`・`br`・`7z`・`yara`・`python3`・`lua`・`gorun`) は PATH 上の本物のコマンドにしてある
    (スクリプトからも呼べる)。
  - それでも出力にこの文言が出たら、名前の挙がったファイルを調べて「見つからない」「CPU が違う」
    「ローダが無い」「SD カード上にあって実行できない」「1 行目の処理系が無い」などの本当の原因と
    直し方を [診断] として表示する。
- **AI に作らせる** — 作りたいものを書くと、この端末で動く形式で作るための条件
  (CPU、Android のバージョン、使えるファイル形式とビルドコマンド、入出力の制約) を付けた
  指示文をコピーできる。ChatGPT や Claude などに貼り付けて使う。
- **APK のインストール** — root の `pm install` で確認画面なしに導入 (上書き更新可)。
  「APK を入れる」のほか、「実行ファイル」で APK を選んでもインストールできる。どちらの入り口でも、
  インストールの前に APK を調べる (`ApkCheck`。端末の中だけで行い、どこにも送らない):
  - 中の実行できる部分 (classes.dex・lib の .so・assets などのスクリプト) を取り出して、ほかのファイルと同じ
    検査 (危険な操作の記述・YARA ルール) をし、APK 全体をウイルスの定義 (ClamAV のハッシュ値) と照合する。
    見つかれば **赤い警告画面** (「詳細」で内容を見てから「それでもインストール」)。
  - 見つからなくても、**認識されない APK** (同じアプリが同じ署名で入っていない、かつ前に許可していない) なら、
    **青いスマートスクリーン** を出す。「詳細情報」で、アプリの名前・パッケージ名・版・発行元 (署名の
    証明書の名前と SHA-256)・注意が必要な権限 (ユーザー補助・SMS・端末管理・ほかのアプリの上に表示など)・
    求める権限の一覧を見てから「それでもインストールする」で進む。同じ中身 (SHA-256) の APK は次から出さない
    (覚えるのは SHA-256 だけで、端末の中に 300 件まで)。同じ発行元の更新 (同じ署名) は出さない。
    同じパッケージが別の署名で入っているときは「偽物の可能性」と出す。
  - このアプリ自身の同じ署名の更新は、中に検査の見本 (危険な操作の記述) を持っているので、記述の検査では止めない
    (ウイルスの定義に一致したときだけ止める)。
  - 確かめたこと (PC で、同じ検査の部分を動かして): F-Droid・Fossify Gallery・Termux・OshiLog・BlockDestroy の
    APK は、どれも危険な記述なし (Termux の中のツール集のファイル名 `bin/mkfs.cramfs` に反応していたので、
    「フォーマット」の項目を、装置 (`/dev/…`) を相手に使う記述だけにした)。
- **Windows Script File (.wsf)** — 「実行ファイル」で .wsf を選ぶと、Wine で動かす。
  Wine 10 の cscript / wscript は .wsf に対応していないので、アプリが .wsf (XML) を読み、選んだ job を
  1 つの .js / .vbs にまとめて (`WsfFile`) D: ドライブに置き、Wine の cscript (メッセージボックスなど画面を
  使うものは wscript。X11 の画面に出る) で動かす。`<object>` は先頭でオブジェクトを作る文に、
  `<resource>` は getResource("id") になる。job が複数あれば選ぶ。
  - 動かす前に、ほかのファイルと同じ検査に加えて、スクリプトの危険な使い方 (ネットから取ってきて保存・起動、
    自動起動への登録、スタートアップへの配置、難読化した中身の実行、一括削除、保護機能の停止) を探す。
    見つかれば **赤い警告画面**、見つからなくても初めて見る中身なら **青いスマートスクリーン**
    (発行元は「不明な発行元」。job・言語・使うオブジェクトの一覧を「詳細情報」に出す)。
  - 動かせないもの (理由を出す): 1 つの job に JScript と VBScript が混ざっているもの、`src=` で別のファイルを
    読み込むもの、暗号化されたスクリプト (.encode)、JScript・VBScript 以外の言語。
  - Wine の制限への対応: Wine の cscript は UTF-16 のスクリプトを読まず、ほかは Windows の文字コードで読むので、
    JScript は英数字だけ (`\uXXXX`) にし、VBScript は Windows の文字コードで書く (日本語の環境なら Shift_JIS、
    そうでなければ日本語は ?。Wine の VBScript では `ChrW` が使えない)。また、Wine の VBScript は、かっこ無しの
    呼び出しの行が CR LF で終わると何もしないので、改行は LF にする。日本語を出すスクリプトは、Wine の
    「日本語の環境で動かす」をオンにすると正しく出る。
  - 確かめたこと (PC の上の qemu で、APK と同じ Box64 0.4.4・同じ wine.sh): `samples/windows/wsf/hello.wsf` の
    JScript と VBScript の job が動き、日本語の環境では日本語も正しく出た。`redscreen-test.wsf` は「危険」になる。
- **コマンドプロンプト (root シェル)** — Windows 風の命令 `dir` `cd` `type` `copy` `move` `ren`
  `del` `md` `rd` `cls` `ver` が使える (`help` で一覧)。プロンプトには今いるフォルダが出る。
  中身は Linux のシェルなので、区切りは `/`、ドライブ名は無い。
  入力欄で `/su` と打つと root モード、`/exsu` と打つと普通のモード (アプリの権限) に切り替わる
  (シェルを起動し直す。選んだモードは次回も使う)。
  シェルが root でないとき (制限モードや、root のシェルが作業領域に入れず root を使わずに
  起動し直したとき) でも、`sudo コマンド` か「root で実行」ボタンで、そのコマンドだけ
  root 権限 (su 経由) で実行できる。root 側でも `dir` などの命令と同梱の `7z`・`yara` が使える。
  端末が root 化されていなければ使えない。
- **エクスプローラー** — root 権限で端末のどこでも見られるファイル画面。テキストは表示、
  バイナリは先頭を 16 進表示する。内部ストレージ・外部 SD カード・アプリの作業領域では
  新規作成・名前変更・コピー・移動・削除・テキスト編集ができる。**システム領域は閲覧のみ**
  (誤操作で端末が起動しなくなるのを防ぐため。変更したい場合はコマンドプロンプトで行う)。
  システム領域のファイルを編集できる場所へコピーすることはできる。
  「選択」(または長押し →「選択」) で複数を選び、まとめてコピー・移動・削除・圧縮できる。
  圧縮は zip か tar.gz で、1 つにまとめることも、1 個ずつ別の圧縮ファイルにすることもできる。
  圧縮ファイルは長押し →「解凍」で、同じ場所に新しいフォルダを作って展開する
  (tar・tar.gz・tar.xz・tar.bz2・zip と、圧縮しただけの .gz / .xz / .bz2)。
  root が無い場合、内部ストレージの編集には「全ファイルへのアクセス」の許可が必要
  (未許可なら開いたときに案内が出る)。
- **検知 (実行ファイルの簡易検査)** — 実行ファイルを開くと、端末を壊したりデータを消したりする
  操作の記述がないか調べる。見つからなければ緑の「スマホが保護されました」を表示してそのまま
  実行できる。見つかれば赤い警告画面で実行を止め、「詳細」で内容を確認したあとの
  「それでも実行」でだけ実行できる。設定で切ることもできる。
- **zip.exe (圧縮・解凍アプリ)** — デスクトップに最初から入っている。ファイルを選んで zip に
  まとめ、パスワードを付ければ AES-256 で暗号化する (WinZip と同じ方式。WinZip・7-Zip・
  Windows 11 のエクスプローラーなどで開ける)。圧縮ファイルを開くと中身の一覧を表示し、
  選んだフォルダへ解凍する。パスワード付きの zip は AES (128 / 192 / 256) と古い方式 (ZipCrypto) の
  どちらも解凍できる。受け渡しは Android のファイル選択画面を通すので、root も
  「全ファイルへのアクセス」の許可も要らない。エクスプローラーの圧縮・解凍でも同じ暗号化が使える。
  zip の決まりで、暗号化されるのは中身だけで、ファイルの名前と大きさは見える。
  パスワード付きで作れるのは合計 4GB・1 個 4GB まで。暗号の計算は Android 標準の機能
  (AES・HMAC-SHA1) だけで行い、外部のライブラリは使っていない。
- **いろいろな形式の圧縮と解凍 (7-Zip 同梱)** — zip.exe・エクスプローラー・「実行ファイル」のどれでも、
  zip・tar・gzip 以外の形式を同梱の 7-Zip 26.06 (`native/build-7zip.sh` でビルドした `7zz`) で扱う。
  - 解凍できるもの: 7z・rar (RAR5 を含む)・zip・tar (gz / xz / bz2 / zst / lzma)・cab・iso・msi・
    wim・deb・rpm・cpio・lzh・arj・dmg・xar・chm・squashfs・仮想ディスク (vhd / vmdk / qcow2) など。
  - 作れるもの: zip・7z・tar.gz・tar.xz・tar.bz2・tar。パスワードを付けられるのは zip (AES-256) と
    7z (AES-256。ファイルの名前の一覧も暗号化する)。rar は作れない (unRAR のライセンスの制限)。
  - **exe の解凍**: インストーラー (NSIS など) や自己解凍形式の exe は、エクスプローラーで長押し →
    「解凍」、または zip.exe で中身を取り出せる。「実行ファイル」から選んだ場合は、展開した中に
    Linux / Android 用の実行ファイルがあればそれを登録できる。
    ただし **Windows 用のプログラムを Linux 用に変換することはできない** (命令は同じ CPU 用でも、
    呼び出す OS の機能がまったく違うため。Wine のような互換層が要り、このアプリには入っていない)。
    インストーラーでも自己解凍形式でもない普通の exe は、解凍もできない。
  - コマンドプロンプトでは `7z x ファイル`・`7z a 名前.7z 対象`・`7z l ファイル` がそのまま使える。
  - 7-Zip は LGPL (一部 BSD)。RAR の展開部分には unRAR の制限 (RAR 圧縮の再現に使わないこと) が付く。
    ライセンス文は 7-Zip のソース配布物の `DOC/License.txt`・`DOC/unRarLicense.txt` にある。
- **ソースをそのまま実行 (`/run`)** — HTML・JavaScript・TypeScript・Go・Python・Lua・
  シェルスクリプトのファイルを、コンパイルなしで実行する。コマンドプロンプトで `/run game.go`
  と打つか、エクスプローラーでファイルを長押し →「実行」。2 つのモードを選べる
  (`/run game.go game`・`/run game.go run` で指定もできる)。
  - **ゲームモード**: 画面で動かす。HTML / JS / TS はアプリの中のブラウザ部品で画面いっぱいに表示する
    (JS / TS だけのファイルにはキャンバスを用意する)。Go / Python / Lua / sh は、色やカーソル移動を
    使える文字端末の画面で動く。どちらも下に操作ボタン (矢印・Space・Enter・Z・X など) が並ぶ。
    プログラムに誤りがあれば、画面にエラーと、その行に印を付けたコードを表示する。
  - **実行モード**: コマンドプロンプトで動かし、出力のあとに終了コードを表示する
    (`print(a)` → `a` / `exit 0`)。JS / TS では `print` と `console.log` が使える。
    30 秒たっても終わらないページは止める。
  - 処理系: JS / HTML は Android の WebView、TS は同梱の TypeScript 5.9 で変換 (型の検査はしない)、
    Go は yaegi (インタープリタ。標準ライブラリと `golang.org/x/term` が使える)、Python は
    MicroPython 1.26 (標準ライブラリは一部だけ。pygame や tkinter などは無い)、Lua は 5.4。
    外部のパッケージ (npm・pip・`github.com/...`) は使えない。
  - C / C++ / Rust / Java などコンパイルが要る言語は実行できない (実行ファイルにしてから
    「実行ファイル」で選ぶ)。言語は `Lang.java` の表に 1 行足せば増やせる。
  - Go の処理系は 1 個 20MB あるので、32bit の x86 用は入れていない。
  - サンプル: [`samples/run`](samples/run) (落ち物ゲームの Go 版・JS 版と、各言語の hello)。
- **画面の上への表示と自動操作 (`br` コマンド)** — 実行したプログラムが、ほかのアプリの上に文字を出したり
  (通信速度の常時表示など)、画面に出ているボタンを探して押したり (自動操作の bot) できる。
  `br overlay set 名前 文字`・`br ui click 文字`・`br ui dump`・`br tap X Y`・`br swipe`・`br key back`・
  `br net`・`br kill パッケージ名` など (`br help` で一覧)。シェルスクリプトからはそのまま、
  C や Go からは `br` を外部コマンドとして呼ぶか、環境変数 `BR_API` の窓口へ直接つなぐ。
  - 既定ではオフ。設定 → 個人設定 →「自動操作と画面上の表示」でオンにする
    (ほかのアプリを勝手に操作できる強い機能なので、信頼できるプログラムを動かすときだけ)。
  - 表示には「他のアプリの上に重ねて表示」の許可、画面の読み取りとボタン押しにはユーザー補助の
    有効化が要る。タップ・スワイプ・戻るなどは、root が使えればユーザー補助なしでも動く。
  - 使っているあいだは通知を出して常駐し、別のアプリを前面にしても動き続ける。通知の「停止」で終わる。
  - 押せるのは、文字か説明が付いているボタンだけ (絵だけのボタンは見つけられない)。
  - サンプル: [`samples/br`](samples/br) (通信速度の表示、「閉じる」ボタンの自動タップ)。
- **実行中のアプリケーションをすべて終了** — デスクトップのタスクバーの「■ すべて終了」か、
  自動操作の bot などが動いているあいだに出る通知の「すべて終了」で、Bionic Runner から動かしている
  プログラムをまとめて止める。広告を閉じる bot などを止めるのに、それぞれのコマンドプロンプトへ
  行かなくてよい。止めるのは、すべてのコマンドプロンプトで実行中のプログラム (その子や孫も。
  root で動かしたものは su 経由で)・画面の上の表示 (br overlay)・X11 と Linux のアプリ・仮想マシンや
  ゲームの画面・切り離して動かしたまま残ったもの。コマンドプロンプト自体は残り、プロンプトに戻る。
  Linux の追加機能のインストールなど apk の作業は、Linux 環境が壊れないよう止めない。
  通知の「表示だけ停止」は、これまでの「停止」(画面の上の表示を消すだけ)。
- **アプリの強制終了** — 設定 →「プログラム」→「Android アプリを強制終了…」で選んだアプリを止める。
  root があればその場で止め、無ければ Android の「アプリ情報」を開く (そこの「強制停止」を押す)。
  プログラムからは `br kill パッケージ名`。
- **仮想マシン (セキュリティ研究用)** — デスクトップの「仮想マシン」から、怪しいプログラムを
  端末から切り離された使い捨ての Linux (Alpine Linux の virt 版) の中で動かせる。
  CPU は ARM64 (端末と同じで速め) と x86_64 (PC 用のプログラムを中で動かす。遅め) から選べる。
  中身は CPU エミュレータ QEMU (`qemu-system-aarch64`・`qemu-system-x86_64`。Termux の Android 用ビルドを
  `fetch-qemu.sh` で取得して同梱) で、root は要らない (QEMU はアプリの権限で動く)。
  - 切り離し方: 中は別の OS (自分専用のカーネル)。ディスクを持たずメモリの上だけで動くので、
    電源を切ると中で起きたことはすべて消え、毎回まっさらな状態から始まる。ネットワークは既定で無し。
  - 調べるファイルは「共有フォルダ」(`files/home/vm-share`。エクスプローラーの「アプリの作業領域」から
    見える) に入れる。中からは読み取り専用のディスク (`/dev/vdb1`) に見え、中から書き換えはできない。
  - Alpine Linux (約 90MB) は APK に入れず、初めて使うときに公式サイトから取ってきて、
    公式の SHA-256 で確かめる。
  - ネットワーク有りでも起動できるが、そのときは QEMU の NAT の仕組み上、中から `10.0.2.2` 経由で
    端末の 127.0.0.1 で待ち受けているものにも届く (起動前に警告する)。マルウェアは無しで動かす。
  - 普段は CPU を真似て (TCG) 動かすので、起動には 1〜数分かかる。64bit の ARM 端末だけで使える。
  - **KVM の診断** (1.44.0〜): 端末の CPU の仮想化の機能 (`/dev/kvm`) を使えるかを、仮想マシンの画面の
    「KVM の診断」で確かめる。以前は `/dev/kvm` に書き込み権限があるだけで KVM を使おうとしていたが、
    権限が `crw-rw-rw-` でも SELinux に拒否されることがあるため、実際に開いて確かめる形に変えた。
    1. CPU のコアの種類を調べる (`/sys/devices/system/cpu/cpu*/regs/identification/midr_el1`。読めなければ
       `/proc/cpuinfo`)。Tensor G3 (Pixel 8) なら Cortex-A510 ×4・A715 ×4・X3 ×1 のように、種類ごとにまとめる。
    2. `/dev/kvm` をアプリの権限と root (使えれば) の両方で開き、仮想マシンと仮想 CPU を作って、
       仮想 CPU で命令を 4 つ実際に動かすところまで確かめる (`native/brkvm.c` → `libbrkvm.so probe`)。
       失敗したら、どの段階で何の理由 (errno) かを出す。プロセスの SELinux の文脈と `/dev/kvm` のラベルも出す。
    3. Alpine Linux を KVM で 2 回ずつ (1 回 45 秒まで) 起動して、「login:」が出るまでの秒数と、毎回起動できたかを
       比べる: コアの種類ごとに固定し、仮想 CPU を 1 個・(一番よいまとまりで 2 個)・そのコアの数 (最大 4) で。
       一番よいまとまりでは、性能カウンタ (PMU) 無し・待ち時間の記録 (steal time) 無しも試し、固定しない場合も 1 つ。
       止まったときは、中の Linux の起動の記録の最後の 12 行を出す (診断のときだけ quiet を外し、earlycon で
       起動のごく最初から出させる)。時間切れのときは、QEMU の監視の画面 (`-monitor unix:…`) に `libbrkvm.so hmp` で
       つないで、仮想 CPU の一覧と各仮想 CPU の命令の場所 (PC)・状態 (PSTATE) を出し、`libbrkvm.so threads` で
       QEMU のスレッドごとの状態 (動いている・眠っている・何を待っているか)・CPU の時間・いたコアも出す。
       コアの固定は `libbrkvm.so pin <コア> -- qemu…` (QEMU を起動する前に自分をそのコアに固定する。
       QEMU のすべてのスレッドに引き継がれる)。
    4. 毎回起動できた設定のうち、固定したもの・仮想 CPU が多いもの・速いものの順で選んで保存する。
       アプリの権限で使えたときだけ、普段の起動 (「3. 起動」) でも KVM を使う (起動の前に毎回すばやく確かめ、
       使えなくなっていれば CPU を真似る形に戻す)。root でしか使えなかったときは、普段の起動では使わない
       (QEMU を root で動かすことになるため。次の段階で扱う)。「KVM を使わない」で設定を消せる。
    - **保護モードの KVM (pKVM)** (1.44.1〜): Pixel 8a (Tensor G3、Android 17) の診断では、`/dev/kvm` は
      アプリの権限では SELinux に拒否され (`untrusted_app` から `kvm_device` を開けない)、root (`u:r:magisk:s0`)
      なら開けて、仮想 CPU で命令も動いた。しかし QEMU は起動直後に `kvm_set_phys_mem: error registering slot:
      Operation not permitted` で止まった (コアを固定してもしなくても同じ)。Android の KVM は保護モード (pKVM) で
      動いていて、「読み取り専用のメモリ領域 (`KVM_MEM_READONLY`)」の登録などを拒否するのに、カーネルは
      「使える」と答えるため、QEMU が ROM やフラッシュの場所をその形で登録しようとするのが原因とみられる。
      そこで、KVM を使うときは QEMU に小さな調整役 `libbrkvmshim.so` (`native/brkvmshim.c`) を `LD_PRELOAD` で
      読み込ませ、「読み取り専用の領域を使えるか」の問い合わせにだけ「使えない」と答える (QEMU はその領域を
      登録せず、装置と同じく自分で処理する)。ほかの呼び出しはそのまま通す。診断ではメモリの登録の結果も出し、
      `probe` で、読み取り専用・書き込みを記録する領域・動かしたあとの追加と削除が通るかも確かめる。
    - Pixel 8a での結果 (1.44.1): 調整役を入れると起動できた。**Cortex-X3 に固定・仮想 CPU 1 個で 3 回とも
      2.6〜2.8 秒** (KVM なしは 6 分たっても終わらない)。仮想 CPU 4 個は、どのコアに固定しても多くが時間切れ
      (A715 で 3 回中 1 回だけ 5.8 秒で起動)。保護モードの KVM は、読み取り専用の領域・書き込みを記録する領域の
      登録と、仮想 CPU を動かしたあとの領域の削除を拒否する (追加はできる)。
    - 1.44.2 の結果: 安定したのは A715 に固定・仮想 CPU 1 個 (6.2 秒)・2 個 (7.9 秒) と X3 の 1 個 (3.2 秒)。
      仮想 CPU 4 個はどこに固定しても多くが止まり、A510 は 1 個でも 1 回止まった。PMU・steal time を切ると
      4 個で 1 回ずつ起動したが、原因そのものではなかった。止まったときは中の Linux の記録が 1 行も出ていない。
      1.44.3 で、止まったときの仮想 CPU の場所とスレッドの様子を調べる。
    - 記録は `files/home/kvm-diag.txt` (エクスプローラーの「アプリの作業領域」) にも保存する。
    - root で試す QEMU は、ネットワーク無し・ディスクへの書き込みを捨てる設定で動かし、測り終わったら
      root で止める (万一止め損ねても `timeout` で 2 分ほどで止まる)。
  - 完全な安全を保証するものではない (QEMU 自体に穴が見つかることもある)。QEMU はアプリの権限で
    動くので、万一破られても Android のアプリとしての制限の中にとどまる。
- **Windows 11 (ARM64) の仮想マシン (試験中、1.45.0〜)** — 「仮想マシン」の画面の「Windows 11 の仮想マシンを開く」から。
  端末の CPU の仮想化の機能 (KVM) を使って、ARM64 版の Windows 11 を QEMU の中で動かす。
  **Windows は試すことはできるが、使い続けるにはライセンス (プロダクトキー) が必要。**
  - 要るもの: root と、「KVM の診断」で root で KVM を使えると確かめてあること。`/dev/kvm` はアプリの権限では
    SELinux に拒否される (Pixel 8a で確認) ので、**QEMU は root で動かす**。コアは診断で安定していた組み合わせに固定する
    (`libbrkvm.so pin`。Pixel 8a では Cortex-A715 (4〜7) に仮想 CPU 2 個がおすすめ。遅いコアのまとまり (A510) は、
    中の Linux が起動のごく最初に「Undefined instruction」で止まったので選択肢から外す)。
  - 部品 (すべて SHA-256 で照合し、合わないものは使わない):
    - UEFI: Debian 13 の `qemu-efi-aarch64` 2025.02-8+deb13u1 (AAVMF、セキュアブート無しの版)。Debian の鍵で署名された
      InRelease → `main/binary-all/Packages.xz` (SHA-256 bb4c324e…f20526) → パッケージ (a00b2411…5276ed) とたどった。
    - ドライバ: virtio-win 0.1.302 の ISO (Fedora のプロジェクトの公式の配布 fedorapeople.org)。配布元には SHA-256 の一覧が
      無い (RPM の MD5 だけ) ので、公式の RPM の中に書かれた ISO の SHA-256 と、直接取ってきた ISO の SHA-256 が
      一致することを確かめて固定した (303f7ae4…67949d)。RPM には署名が無いので、確かめられるのは「公式の場所の 2 つの
      配布物が同じ」ところまで。中に Windows 11 の ARM64 用のドライバ (NetKVM・viogpudo・vioinput など) がある。
    - **Windows 11 の ISO はアプリにもリポジトリにも入れないし、代わりに取ってくることもしない。** 利用者が Microsoft の
      公式サイトから ARM64 版をダウンロードして選ぶ (「ダウンロード」の ISO が一覧に出る)。名前に ARM64 が無ければ注意を出す。
  - 仮想マシンの形: `virt` (GIC は端末と同じ版)・`-cpu host`・メモリ 3/4/6GB (端末のメモリに合わせて 4GB が目安。
    全体から 2.5GB 引いた量より多いと警告、今の空きより多いと警告)・画面は ramfb (+ 設定で virtio-gpu。Windows に
    viogpudo を入れたあと)・入力は qemu-xhci + usb-kbd + usb-tablet (タッチした場所にそのままポインタが動く)・
    ディスクは NVMe (Windows に最初からドライバがある) の 64GB の qcow2 (内部ストレージ。中身の分だけ大きくなる。
    アプリが qcow2 の形を自分で書く。作る前に空きを確かめ、32GB 未満なら警告)・CD は USB の記憶装置
    (Windows の ISO・virtio-win・要件の確認を外す設定ファイルの読み取り専用の FAT)。ネットワークは初めは無し
    (設定で NAT の virtio-net を付けられる。中から 10.0.2.2 経由で端末の 127.0.0.1 にも届くので警告する)。
  - **保護モードの KVM の対策 (フラッシュの形)**: UEFI はフラッシュの上の命令をそのまま実行するが、pKVM は読み取り専用の
    メモリ領域と、動かしたあとの登録の削除を拒否する。そこで `libbrkvmshim.so` を `BRKVM_SHIM_FLASH=1` で読み込ませ、
    1 つ目のフラッシュ (UEFI の本体。0x04000000 より下) はふつうのメモリとして登録し、それ以外の読み取り専用の登録
    (2 つ目のフラッシュ = UEFI の設定の保存場所など) は登録したことにして読み書きを QEMU に任せる (設定の書き込みの手順の
    途中の削除も、消したことにする)。書き込みを記録する印は外す。
  - 画面: QEMU の VNC を 127.0.0.1 だけで待ち受け、毎回作る 8 文字のパスワードを付ける (ほかのアプリから 127.0.0.1 に
    つながれても操作されないように。パスワードはアプリ専用の場所のファイルで QEMU に渡す)。アプリの VncView が VNC の
    パスワード認証 (DES。端末に頼らず自分で計算する。PC の Java の DES と 2000 通りで一致を確認) でつないで映す。
    画面の下のボタンで、キーボード・Esc・Tab・Win・Ctrl・Alt・Shift+F10・Ctrl+Alt+Del・矢印・右クリック。
    VNC はキー (X の keysym) を PC のキーの番号に直すのに対応表 (keymaps) を使う。Termux の QEMU では別のパッケージ
    `qemu-common` に入っているので、同じ版 (1:11.1.3) を署名付きの一覧 (InRelease → Packages.gz → パッケージ) の
    SHA-256 で照合して取り出し、同梱物の `fw/keymaps/` に足した (1.45.2。`fetch-qemu.sh` も取るように直した)。
    キーボードの配列は Windows の側に合わせて日本語 (JIS、既定) か英語 (US) を選ぶ (`-k ja` / `-k en-us`)。
    画面を閉じても仮想マシンは動き続ける (QEMU は `-daemonize` で裏に回る)。止めるのは Windows の中から、
    「シャットダウン」(Windows に電源ボタンを伝える)、または「強制終了」。
  - **要件の確認 (TPM・セキュアブートなど) を外す手順**を画面と、付ける FAT のドライブの README.txt に書いた。
    「要件の確認を外す設定ファイルを付ける」(既定で入) を入れると、そのドライブの `autounattend.xml` がインストールの
    始めに読み込まれ、`HKLM\SYSTEM\Setup\LabConfig` の BypassTPMCheck・BypassSecureBootCheck・BypassRAMCheck・
    BypassCPUCheck・BypassStorageCheck を 1 にする (ほかは何も自動にしない。言語・ディスク・アカウントはいつも通り画面で選ぶ)。
    初期設定でネットワーク無しで進めるための BypassNRO も入れる。手で外すための `bypass.cmd` も置く (Shift+F10 から)。
  - 確かめたこと (PC の QEMU。KVM は無いので CPU を真似る形で、同じ装置の組み合わせ): UEFI が ramfb に出て、USB の CD
    (起動できる ARM64 の ISO として Alpine を使用) から起動した。virtio-gpu の形でも起動した。3 つの CD は USB 3 に
    つながった。アプリが作った qcow2 を `qemu-img check` が正しいと判定し、書いた分だけ大きくなった。VNC は
    正しいパスワードでだけつながった。調整役のフラッシュの形は、登録・削除の呼び出しを真似た試験で思った通りに動いた。
    **Pixel 8a で、KVM で UEFI が起動して画面が映り、Windows の CD・設定ファイルのドライブ・NVMe のディスクが
    見えた (1.45.2)。** ただし CD の「Press any key to boot from CD or DVD…」(5 秒) に間に合わず UEFI のシェルに
    なったので、1.45.3 から、まだ Windows が入っていない (ディスクが 2GB 未満) あいだは、起動から 25 秒だけ
    QEMU の監視の画面の `sendkey spc` で 1 秒ごとに空白のキーを押す。シェルになったときの手順 (`FS0:` →
    `\efi\boot\bootaa64.efi`) も画面に書いた。Windows のインストールが最後まで進むかはまだ確かめていない。

- **X11 (Xサーバー)** — デスクトップの「X11」(またはコマンドプロンプトで `x11`) で、Linux 用の
  X のアプリ (xterm など、ウィンドウを持つもの) を動かして、その画面をアプリの中に映せる。root は要らない。
  - 仕組み: アプリの中に Linux 環境 (Alpine Linux の最小構成 minirootfs) を作り、同梱の PRoot
    (`libproot.so`。Termux 版 (GPL-2.0) を `native/build-proot.sh` でビルド) で「その中にいるように見せて」動かす。
    X サーバーはその中の Xvnc (TigerVNC)。アプリの画面が VNC の手順で映して、操作を送る。
  - 初めて開いたときに Alpine Linux (約 4MB) を公式サイトから取ってきて公式の SHA-256 で確かめ、
    中で `apk add tigervnc xterm twm xsetroot font-misc-misc` を実行する (100MB ほどダウンロード。
    展開後は 300MB ほど)。最初の画面は、ウィンドウの枠 (twm) と端末 (xterm)。新しい窓は自動で置かれる。
  - 操作: 軽く触る = 左クリック、なぞる = スクロール (スマホと同じ向き。上下・左右)、
    長押しして離す = 右クリック、長押し (振動したら) してなぞる = 左ボタンを押したまま動かす
    (文字の範囲選択・ウィンドウの移動)、2 本指 = 拡大・縮小と移動。下のボタンで ⌨ (キーボード)・Esc・Tab・Ctrl・Alt
    (次のキーに付く)・矢印・右クリック・ホイール・貼り付け (Android でコピーした文字)・全体表示。
    X の中でコピーした文字は Android のクリップボードに入る。
  - **ホーム画面から起動**: 追加機能で入れた画面を持つアプリ (Chromium・Firefox・GIMP など) は、デスクトップ
    (表示が「全部」か「その他」のとき) にアイコンが出る。押すと X11 の画面を開き、X サーバーが止まっていれば
    起動してから、そのアプリを起動する (アイコンからは、アプリが知っている追加機能のアプリだけを起動する)。
  - **ダウンロードの保存先**: アプリが内部ストレージに書き込めるとき (「全ファイルへのアクセス」を許可したとき) は、
    Chromium・Firefox でダウンロードしたものを端末の Download フォルダ (中では /sdcard/Download) に保存する
    (ブラウザの設定 (ポリシー) を、Linux 環境を用意するたびに書く。利用者が自分で書いた Firefox の設定は触らない)。
    書き込めないときは、Linux 環境の中の /root/Downloads に保存される。
    Alpine 版の Chromium では Google の安全確認 (セーフ ブラウジング) が働かず、ダウンロードが
    「Unconfirmed 123456.crdownload」のまま利用者の確認を待って止まるため、確認待ちにしない設定
    (`DownloadRestrictions: 0`・`SafeBrowsingProtectionLevel: 0`) も書く。Download に入ったファイルは、
    セキュリティのリアルタイム保護 (オンのとき) が、名前が確定したところで調べる。
  - **Linux の追加機能** — デスクトップの「Linux の追加機能」(X11 の画面の「追加機能」ボタン、
    `x11 addons` でも開ける) で、使いたいものを選んで「ダウンロード」を押すと入る。アプリには同梱せず、
    押したものだけを Alpine Linux の公式の配布元から apk で取ってくる。入っているものは「削除」で消せる。
    入れる作業は画面を閉じても最後まで続く。並んでいるもの (ダウンロードの目安):
    日本語フォント (75MB)・Chromium (230MB)・Firefox (160MB)・Xfce デスクトップ (165MB)・
    Mousepad・Geany・PCManFM・GIMP・LibreOffice (320MB)・VLC・Python 3・開発ツール (gcc・git)・
    Thunderbird (メール・125MB)・Evince (PDF)・Ristretto (画像)・Krita (お絵描き・155MB)・Inkscape (SVG)・
    Xournal++ (手書きノート)・AbiWord (文書)・Gnumeric (表計算)・Galculator (電卓)・KeePassXC (パスワード管理)・
    FileZilla (FTP)・Xarchiver (圧縮)・Thunar (ファイル)・DOSBox・端末の道具 (neovim・htop・tmux)・
    Node.js と npm・OpenJDK 21 (160MB)・Go (114MB)・glxgears・xeyes。
    (Alpine Linux 3.24 の aarch64 の一覧で、名前があることと、Xサーバーの分を除いたダウンロードの大きさを確かめた。
    音を出せないので、音楽・動画の編集ソフトは並べていない)
    - 画面を持つアプリは、X11 の画面の「アプリ」ボタンで選んで起動する。X の背景から指でなぞると出る
      twm のメニューにも並ぶ (メニューは「Reload menu」で入れ直したものを読み直す)。
      コマンドプロンプトからは `linux chromium &` のように起動できる。
    - Chromium は、proot の中ではページごとの隔離 (サンドボックス) が使えないため、`--no-sandbox` で動く
      (設定は `/etc/chromium/zz-bionic-runner.conf`)。信用できないサイトは開かないこと。
    - Xfce を入れると、次に X を起動したときから X11 の画面が Xfce のデスクトップになる
      (`/root/.xsession` を置けば、そちらが優先)。
    - GTK の画像の読み込み (glycin) が使う隔離の道具 bwrap も proot の中では動かないので、隔離をせずに
      そのまま実行する代わりのもの (`/usr/local/bin/bwrap`) を置いている。
  - 一覧に無いものも、コマンドプロンプトで `linux` と打って Linux 環境に入り (`exit` で戻る)、
    `apk add アプリ名` で入れられる (`DISPLAY=:1` は設定済み)。
  - X サーバーは X11 の画面を閉じても動き続ける (開き直すと続きが見える)。止めるのは「X を終了」か
    `x11 stop`。Linux 環境ごと消すには、接続が切れたときの画面の「Linux 環境を削除」。
  - 端末の内部ストレージは、中から `/sdcard` に見える (読める場合)。
  - apk は同時に 1 つしか動かせない。2 つ目は前のものが終わるまで待つ (`/etc/apk/config` に `wait 300`)。
    初回の準備の途中で X11 の画面を閉じても準備は続き、開き直すとその続きが表示される。
  - VNC の接続口は TCP ではなく、アプリだけが入れる場所の UNIX ソケットなので、同じ端末のほかの
    アプリから X の画面を覗いたり操作したりはできない。
  - root のシェル (`/su`) から `linux` を使うと、アプリの権限に戻して動かす (中のファイルの持ち主を
    揃えるため)。
- **セキュリティ (ウイルス対策)** — デスクトップの「🛡 セキュリティ」。PC の「Windows セキュリティ」のように、
  保護の状態・スキャン・リアルタイム保護・ウイルスの定義の更新・隔離・保護の履歴をまとめて扱う。
  - **スキャン**: クイック (ダウンロード・ドキュメント・Bluetooth・メッセージアプリの受信ファイル
    (Android/media)・登録したプログラム)、フル (内部ストレージ全体・アプリの作業領域・インストール済みの
    アプリの APK)、カスタム (フォルダを選ぶ)。画面を閉じても続く。見つかったものは「隔離」「削除」
    「許可」(今後は検出しない) を選べる。インストール済みのアプリなら「アンインストール」。
  - **検査の中身**: オープンソースのウイルス対策エンジン ClamAV 1.5.4 (Termux の Android 用ビルドを
    `fetch-clamav.sh` で同梱。64bit の ARM 端末だけ) と、その公式の定義 (約 360 万件)。あわせて、追加した
    YARA ルールと、実行ファイルに書かれた危険な操作 (`ExeScanner`。「疑わしい」として出す) も調べる。
    ClamAV のエンジンは定義を読み込むのに 1GB ほどメモリを使い、読み込みに 1 分ほどかかる。
    メモリ不足で止められたときや、エンジンの無い端末では、内蔵の検査 (下) で調べる。
  - **リアルタイム保護**: オンにすると常駐し (通知が出たままになる)、上の場所にファイルが置かれたり
    書き換えられたりしたら、すぐ調べる。見つけたときの処置は 3 つから選ぶ: 「隔離する」(既定。あとで
    復元できる)・「問答無用で削除して、通知だけ来る」(確認なしですぐ消す。元に戻せない)・
    「何もせず、通知だけ来る」。「疑わしい」もの (危険な操作が書かれた実行ファイル) も対象にするかを
    スイッチで選べる (既定は対象にする)。
    エンジンを毎回読み込むと重すぎるので、ここでは内蔵の検査を使う: 定義のうち「ファイル全体の
    ハッシュ値」の約 54 万件を小さな索引 (約 13MB) にして照合し、テスト文字列 (EICAR)・YARA ルール・
    危険な操作の記述も調べる。端末の起動時にも、オンなら自動で始まる。
    - **新しいファイルの見つけ方** (1.42.0 から 3 つ。どれかで気づけばよく、同じ中身のファイルは二度調べない):
      1. ファイルの変化の知らせ (FileObserver)
      2. Android のメディアの一覧 (MediaStore) の変化。ブラウザやダウンロードの仕組みが保存したファイルは、
         1 の知らせが来ないことがあるため (それまでは、これで検出されないことがあった)
      3. 20 秒ごとの見回り: 前回より後に中身が変わったフォルダだけを開いて、新しいファイルを探す
    - **全ファイルへのアクセス**: ほかのアプリ (ブラウザなど) が置いたファイルを読むには、Android 11 からは
      この許可が要る。リアルタイム保護をオンにしたときに許可が無ければ、理由を出して設定の画面を開く。
      無いあいだは、常駐の通知とセキュリティの画面に「全ファイルへのアクセスがありません」と出す。
    - **調べる中身** (1.42.0 で広げた): Windows のプログラム (先頭が MZ なら拡張子に関係なく。文字列の検査と、
      構造の検査で「危険」のもの)、Windows のスクリプト (.bat・.cmd・.ps1・.vbs・.wsf・.hta。WSF はスクリプトの
      危険な使い方も)、APK (中の dex・.so・スクリプト。このアプリ自身の同じ署名の更新は除く)、zip の中の EICAR。
    - **動作の確認**: セキュリティの画面の「動作を確かめる」で、害の無いテスト用のファイル (EICAR) を
      ダウンロードのフォルダに置く。数秒〜20 秒で検出の通知が出て、設定した処置 (隔離など) が行われる。
  - **定義の更新**: 「定義の更新」で ClamAV の公式の配布元 (database.clamav.net) から main.cvd・daily.cvd
    を取る (初回は約 110MB。2 回目からは新しい版があるものだけ)。ファイルの頭に書かれた MD5 で
    中身を確かめ、エンジンも読み込むときに ClamAV の署名を確かめる。定義はアプリに同梱しない。
  - **隔離**: 中身を変換して (そのままでは実行も検出もされない形にして) アプリの中にしまい、元の
    ファイルを消す。「復元」で戻す (そのファイルは以後「許可」扱い)、「完全に削除」で消す。
  - 実行ファイルや圧縮ファイルを開くときの検査 (`ExeScanner`) でも、定義のハッシュ値と照合する。
  - ウイルス対策アプリと同じく、すべての脅威を見つけられるわけではない。ClamAV は PC (Windows) 向けの
    定義が多く、Android のアプリ (APK) の検出は専用のウイルス対策アプリほど強くない。
- **Linux の実行ファイル (ELF) の名前** — 登録した ELF の名前には、元の拡張子に関係なく種類の拡張子が付く:
  bionic 用は `名前.Belf`、glibc 用は `名前.Gelf`、そのほか (静的リンクなど) は `名前.elf`
  (元の `.bin`・`.elf`・`.out`・`.so` などは外してから付ける)。コマンド名もこの名前になる
  (例: `game.Belf`)。前の版で登録したものも、起動時に名前を付け直す (アイコン・デスクトップの並びも引き継ぐ)。
  圧縮ファイルから展開したもの (tar.gz など) とスクリプトは、名前を変えない。
- **mkexe (端末の上で実行ファイルを作る)** — コマンドプロンプトで `mkexe ソース.c` と打つと、C のソースから
  bionic (Android) 用の実行ファイルを作る (`-t glibc` で glibc (Linux) 用)。引数なしの `mkexe` は対話形式。
  コンパイラは同梱の TCC (`native/build-tcc.sh` で NDK を使ってビルド。64bit の ARM 端末だけ)。libc の
  ヘッダとライブラリは初めて使うときに公式の配布元 (Termux の ndk-sysroot・Debian 13 の glibc 2.41) から
  取ってきて SHA-256 で確かめる。できるファイルの名前は、bionic 用が `名前.Belf`、glibc 用が `名前.Gelf`。bionic 用は `./名前.Belf` で、
  glibc 用は `mkexe run 名前.Gelf` で動く。
  詳しい使い方と確認したことは [`samples/mkexe`](samples/mkexe)。C++ は使えない。
- **専用キーボード** — 普通の Android のキーボードに無い Esc・F1〜F12・Ctrl・Alt・Shift・Win (Meta)・
  矢印・Home/End・PgUp/PgDn・Ins/Del のあるキーボード。Android の「入力方法」として入っているので、
  ターミナル・X11 のほか、どのアプリでも使える。日本語入力は無い (英数字と記号だけ)。
  打った内容は保存も送信もせず、ログにも出さない (保存するのはキーの高さの設定だけ)。
  - **有効にする (最初の 1 回)**: コマンドプロンプト・X11・ゲームモードの画面の「⌨ 専用キーボード」を押すと
    手順が出る。「設定を開く」→ 一覧の「Bionic Runner 専用キーボード」をオン (Android の決まった注意が出る)
    → 戻ってもう一度「⌨ 専用キーボード」を押して選ぶ。Android の設定 → システム → キーボード からでもよい。
  - **切り替え**: 「⌨ 専用キーボード」でキーボードの一覧が出る。元に戻すのは専用キーボードの 🌐
    (長押しで一覧)。「⌨ 専用キーボード」の長押しか、キーボードの ⚙ で設定 (キーの高さを縦画面・横画面
    それぞれ 28〜72dp で変えられる。試し打ちの欄つき)。
  - **キー一覧**:

    | 段 | キー |
    |---|---|
    | 1 段目 (横に流せる) | Esc F1〜F12 Ins Del Home End PgUp PgDn ⚙ |
    | 2 段目 | `` ` `` 1〜0 - = (Shift で ~ ! @ # $ % ^ & * ( ) _ +) |
    | 3 段目 | q〜p [ ] \ (Shift で { } \|) |
    | 4 段目 | Tab a〜l ; ' |
    | 5 段目 | Shift z〜m , . / ⌫ |
    | 6 段目 | Ctrl Alt Win 🌐 Space ← ↑ ↓ → Enter |

  - Ctrl・Alt・Shift・Win は、1 回押すと次の 1 キーだけ有効 (青)、2 回押すと固定 (濃い青・黄色の字)、
    もう一度押すと解除。キーは長押しで繰り返す。
  - 送り方: 普通の文字は文字として渡し、Ctrl・Alt・Win と一緒のときや特別なキーは、正しい keyCode と
    metaState (CTRL_ON など) のキーとして送る (Ctrl+C・Alt+Tab・Ctrl+Alt+Del なども届く)。
    1 行の入力欄で Enter を押すと、その欄の決まった動作 (送信など) をする。
  - ターミナルでは xterm と同じバイト列になる (`KeySeq`): 矢印 `ESC[A`〜 (vim などが使う
    アプリケーションカーソルモード `ESC[?1h` では `ESCOA`〜)、Home/End `ESC[H`/`ESC[F`、F1〜F4 `ESCOP`〜`ESCOS`、
    F5〜F12 `ESC[15~`〜`ESC[24~`、Ins/Del/PgUp/PgDn `ESC[2~`/`ESC[3~`/`ESC[5~`/`ESC[6~`、修飾キー付きは
    `ESC[1;5D` (Ctrl+←) のように番号付き、Shift+Tab `ESC[Z`、Ctrl+文字は制御文字、Alt+文字は ESC 付き。
    コマンドプロンプトでは、Ctrl+C で中断、F1〜F12・Esc・Tab・↑↓・PgUp/PgDn・Ctrl/Alt の組み合わせを
    実行中のプログラムへ送る。入力欄の編集 (←→・Home・End・Backspace・Ctrl+V など) はこれまでどおり。
    全画面の表示中で入力欄が空なら、←→・Backspace もプログラムへ送る。
  - X11 では対応する X のキー (keysym) として届く (Shift・Win も付く。Win は Super_L)。
- **YARA ルール** — 「実行ファイル」から `.yar` / `.yara` を選ぶと、書き方を確かめたうえで
  「検知に追加」か「ファイルをスキャン」を選べる。検知に追加したルールは、実行ファイルや
  圧縮ファイルを開くときの検査で一緒に使われ、一致すると赤い警告画面で実行を止める
  (設定の「個人設定」で外せる)。「ファイルをスキャン」は選んだファイルをその場で調べて結果を表示する。
  コマンドプロンプトでは `yara ルール 対象` (フォルダごとは `yara -r`) がそのまま使える。
  追加済みのルールの置き場所は `$BR_YARA_RULES`。
  中身は同梱の YARA 4.5.2 (`native/build-yara.sh` でビルド)。pe・elf・math・dotnet・macho・dex
  などのモジュールは使えるが、`hash` モジュール (md5 / sha256 など)・magic・cuckoo は入っていない。
- **設定** — システム情報 (機種・Android・CPU 使用率・メモリ・ストレージ)、タスクマネージャー
  (CPU を使っている順のプロセス一覧と終了)、プログラム (実行ファイルと APK のインストール、
  実行ファイルと Android アプリのアンインストール)、個人設定 (壁紙・検知の入切)。
- **色とカーソル移動 (ANSI エスケープシーケンス)** — コマンドプロンプトのログ表示でも、文字の色の指定
  (文字色 30〜37・90〜97、背景色 40〜47・100〜107、太字、リセット、256 色、24bit 色) を反映するので、
  `ls --color=always` や `grep --color=always` の出力が色付きで読める。画面全体に描くプログラム
  (画面消去 `ESC[2J`・カーソル位置の指定 `ESC[行;列H`・代替画面 `ESC[?1049h` を出すもの。
  文字の雨や htop・btop など) が動くと、ゲームモードと同じ文字端末の画面に切り替わり、
  80×24 文字の画面として正しく描かれる (カーソルの表示・非表示にも対応)。
  プログラムが終わるか、代替画面を抜けると、元のログ表示に戻る (それまでのログは残る。
  代替画面を使わないプログラムは、最後に描いた画面をログに残す)。右下の「ログに戻る」でも戻れる。
  全画面のあいだも、下の入力欄・送信・「中断 ^C」は使える。対応していないエスケープシーケンスは、
  文字として出さずに捨てる。サンプル: [`samples/ansi/matrix.sh`](samples/ansi/matrix.sh) (文字の雨)。
- **入力欄** — 下の入力欄からコマンドを直接実行。実行中のプログラムへの入力にもなる。
  「中断 ^C」で実行中のコマンドに SIGINT を送る。
  複数行を貼り付けると (Termux と同じように) 1 行ずつ実行する。1 行目のコマンドが終わってプロンプトに
  戻ってから 2 行目を送るので、前のコマンドが次の行を入力として読んでしまうことがない
  (`for` 文など、続きの入力を待つ途中のプロンプトでも次の行を送る)。「中断 ^C」で残りの行を取り消す。
- Debian のパッケージ (.deb) も、圧縮ファイルと同じように選べる。外側 (ar) を開いたあと、中の data.tar.* を
  続けて展開し、その中の実行ファイルを選んで登録する。glibc 用のプログラムは、動くのに必要なライブラリのうち
  アプリにもパッケージの中にも無いものを登録の画面に出す (Google Chrome のような、Debian・Ubuntu の多くの
  ライブラリを使う大きなアプリは動かない。ブラウザは「追加機能」の Chromium を使う)。
- ファイルマネージャの「アプリで開く」から APK / 実行ファイルを受け取れる。

## 必要なもの

- Android 7.0 (API 24) 以上
- root は**あれば使う**。無くても、登録したプログラムやゲームの実行、エクスプローラーでの
  内部ストレージの閲覧・編集 (「全ファイルへのアクセス」の許可が必要) はできる。
  root が必要なのは、APK の確認なしインストール、システム領域の中の読めないファイルの閲覧、
  タスクマネージャー、静的リンクの ELF の実行。
- root を使う場合は Magisk / KernelSU / APatch など `su` が使えること。
  このアプリ自体は端末を root 化しない。
  - Magisk: アプリの起動時に出る許可の確認画面で許可する。以前に拒否したか時間切れに
    なった場合は確認画面が出ないので、Magisk アプリの「スーパーユーザー」でオンにする。
  - KernelSU / APatch: 確認画面は出ない。管理アプリの「スーパーユーザー」で許可する。
  - Magisk で「root の権限を制限する」設定がオンだと、uid は 0 でも権限 (ケーパビリティ) が
    すべて外され、root のシェルからアプリの作業領域に入れない。その場合は [診断] に直し方を表示し、
    root を使わずに起動し直す。設定をオフにして「再起動」を押せば root で動く。
  - タスクバーの「root ✔ / ✖」か、コマンドプロンプトの「root 確認」を押すと、
    使えない原因 (su が無い・拒否された) と直し方が表示される。
- root が無い場合は「制限モード」で起動する: APK は標準インストーラ経由になる。
  bionic 動的リンクの実行ファイル (システムのローダ経由)、glibc 動的リンクの実行ファイル
  (アプリの `lib/` のローダ経由)、スクリプトは実行できる。

## 実行できないもの

- メモリのページが 16KB の端末 (Android 15 以降の新しい機種) で、4KB 境界で作られた ELF。
  ファイルを開いたときにその旨を表示する。`-Wl,-z,max-page-size=16384` を付けて
  ビルドし直せば動く (GNU の gcc と Go は既定で満たす。NDK r27 以前は指定が必要)。

- Windows の `.exe` (PE 形式) は Wine で動かす (上の「Windows のプログラム (Wine)」)。32bit の exe は試験中
  (追加機能で 32bit の部品を入れたときだけ)。
- musl を動的リンクしたバイナリ (静的リンク版なら動く)。
- 同梱以外の共有ライブラリ (libz, libssl など) が要る glibc バイナリ。必要な `.so` を
  `files/glibc/<ABI>/lib` に root で置けば読み込まれる。
- glibc 2.44 より新しい環境でビルドした glibc バイナリ。
- 端末と CPU が違うバイナリのうち、エミュレータの無い CPU 用 (MIPS・ppc64le など)。
- コマンドプロンプトでの、1 文字単位のキー入力 (`vi` や `top` の操作など)。画面は全画面モードで
  正しく描かれるが、キーは入力欄から 1 行ずつ (Enter 付きで) 送ることになる。1 文字ずつのキー操作が
  要るゲームなどは `/run ファイル game` (ゲームモード) で動かす。
- OpenGL / Vulkan で描画するゲーム (3D ゲームの大半)、X11 や Wayland を直接使う GUI アプリ。
  絵が出せるのは SDL2 (または SDL 1.2) のソフトウェア描画を使うプログラムだけ。

## 検知について

ファイルに含まれる文字列 (スクリプトなら各行、バイナリなら埋め込まれた文字列) から、
次のような操作の記述を探す (`ExeScanner`)。

- ストレージやパーティションへの直接書き込み、フォーマット (装置 `/dev/…` を相手にしたもの)、起動領域の書き換え
- `/`・`/system`・`/data`・`/sdcard` などの一括削除、端末の初期化
- システム領域を書き込み可能にする変更、SELinux などの保護の無効化
- アプリの削除・無効化、フォーク爆弾
- ネットから取得した命令の実行、遠隔操作、認証情報の読み取り
- ウイルス検査用のテスト文字列 (EICAR)。警告画面の動作確認に使える

**記述を探すだけの簡易検査で、ウイルス対策ソフトではない。** 文字列を隠したプログラムや、
危険な操作をシステムコールで直接行うバイナリは見逃す。逆に、ディスク管理ツールのような
正当なプログラムを危険と判定することもある。緑の表示は「安全の保証」ではない。

PC 上での確認: Debian のゲーム 6 本と無害なスクリプト 2 本、補助プログラムは「安全」、
危険な操作を書いたスクリプト 10 本・EICAR・データを消す ARM64 バイナリは「危険」と判定された。

### Windows の exe の構造の検査 (`PeInfo`・`ExeScanner.scanPe`)

文字列を探すだけでは、危険な部分を暗号化して隠す「ローダー型」のウイルス (書き込みも実行もできるメモリを取り、
暗号を解いた命令を動かし、設定はファイルの末尾に付け足したデータに入れておく、など) を見逃す。そこで Windows の
exe・dll (32bit・64bit) は、作り (構造) も調べる。ファイルは先頭から 64MB までしか読まず、壊れたファイルや
わざと壊したファイルでも止まらない (範囲の確認・数の上限・回数の上限)。端末の中だけで調べ、どこにも送らない。

1 つの特徴だけでは危険とは言えないので、特徴ごとの点数の合計で判定する。

| 特徴 | 点数 |
|---|---|
| 実行するときに、書き込みも実行もできるメモリを用意する (VirtualAlloc・VirtualProtect と CreateThread など、または「書き込みも実行もできる」と指定している箇所) | 3 |
| ほかのプログラムに命令を書き込んで動かす (OpenProcess + VirtualAllocEx + WriteProcessMemory + CreateRemoteThread・QueueUserAPC・SetThreadContext) | 6 |
| 書き込みも実行もできるセクション | 3 |
| 中身がランダムに近いセクション (ばらつき 7.2 以上・4KB 以上。絵や音の部分は除く) | 3 |
| 末尾に付け足されたデータが 1MB 以上、またはランダムに近い (署名とデバッグ用の記号の表は除く) | 3 |
| 使う関数がほとんど無い (LoadLibrary と GetProcAddress だけ、など) / ひとつも無い | 3 / 2 |
| 圧縮の道具の印 (UPX・ASPack など) / 解析を難しくする道具の印 (Themida・VMProtect など) | 2 / 3 |
| 最初に動く場所が、コードの部分の外 (最後のセクションなど) | 3 |
| メインの処理より前に動く仕組み (TLS コールバック) | 1 |
| キー入力の記録 (SetWindowsHookEx + キーを文字にする関数、GetAsyncKeyState + 前面のウィンドウ) ・画面の取り込み (BitBlt + GetDC + 画面全体 + 保存) | 3 |
| 自分自身のファイルを読み (GetModuleFileName + CreateFile + ReadFile)、末尾に付け足したデータがある | 3 |
| 壊れた PE | 3 |

ほかの DLL への取り次ぎ (自分でも同じ名前の関数を提供しているもの。Windows 自身の DLL に多い) は数えない。

**判定: 5 点以上で「要注意」、8 点以上で「危険」。** 「要注意」以上なら、登録の画面と「Wine で実行」の確認で、
見つかった特徴と理由を一覧で見せ、「それでも実行する」を押さないと実行しない。ClamAV の定義があれば、その照合の
結果 (ファイル全体のハッシュ値) も一緒に出す。

しきい値の決め方 (`tools/run-pe-tests.sh` で確かめられる。単体テストは `app/src/test/java/…/PeScannerTest.java`):

- 誤判定: Wine 10.0 に付いている exe と dll 750 個 (PE でない 2 個を除く) は、0 点が 743 個・3 点が 7 個で、
  最高は 3 点 (特徴 1 つ)。だから「要注意」は特徴が 2 つ以上そろう 5 点からにした
- 見逃し: `samples/windows/scanner-test/` の確認用の exe (ローダー型の特徴だけを持つ害の無いもの。64bit と 32bit) は、
  どちらも 10 点 (メモリの準備 3・末尾のデータ 3・自分を読む 3・TLS 1)。特徴が 3 つそろう 8 点を「危険」にした
  (TLS の 1 点が無くても 9 点で「危険」のまま)。この 2 つは、文字列の検査では何も見つからない

**これも完全ではない。** 名前でなく実行中に関数を探す作り (点数は付くが、ほかの特徴が無ければ「問題なし」になる) や、
ふつうのプログラムと見分けがつかない作りのウイルスは見逃す。インストーラーや保護ツールを使った正当なプログラムが
「要注意」になることもある。ClamAV の照合はファイル全体のハッシュ値だけで、PE のセクションごとの定義 (.mdb) は使っていない。
登録したあとにデスクトップのアイコンから動かすときは、検査をし直さない。

## 絵と音の仕組み

同梱の glibc 一式に、出力先をこのアプリに差し替えた SDL2 を入れてある
(`native/sdl/` が差し替えたドライバ、`native/build-sdl.sh` がビルド手順)。

- プログラムが SDL2 でウィンドウを作ると、SDL2 がアプリ内のサーバ (127.0.0.1) に接続し、
  フレームと PCM 音声を送る。接続先と合言葉はシェルの環境変数 `BR_DISPLAY` で渡している。
- 同梱ライブラリ: SDL2 2.32.10、SDL2_image (PNG・JPG・BMP・GIF など)、
  SDL2_mixer (WAV・OGG・MP3・FLAC)、SDL2_ttf、SDL 1.2 互換 (`libSDL-1.2.so.0`)。
  SDL2 を**動的リンク**しているプログラムが対象で、SDL2 を静的に取り込んだものや、
  ここに無いライブラリ (SDL_net、SDL 1.2 用の SDL_image / SDL_mixer など) が要るものは動かない。
- 描画はソフトウェア描画のみ。OpenGL のコンテキストは作れない。
- ゲームのデータファイルが決まった場所 (`/usr/share/...`) に必要なプログラムは、
  そのままでは動かない (実行ファイル 1 個で完結するものが向いている)。
- root は不要 (root なしでの実行は実機で未確認)。

## 動作確認したゲーム

Debian の `bsdgames` (arm64・glibc 動的リンク) を、アプリと同じ経路 (同梱 glibc + ptyrun +
1 行ずつの入力) で PC 上のエミュレーションにより確認した。Android 実機での確認ではない。

| ゲーム | 結果 |
| --- | --- |
| Colossal Cave Adventure、Hunt the Wumpus、go-fish、arithmetic | 遊べる |
| tetris-bsd など curses を使うもの | 起動しない (libncurses が無い。入れても画面描画に非対応) |
| Sopwith (Debian の arm64 版、SDL2) | タイトル画面とプレイ画面の表示、キー入力、音声の送出を確認 |
| SDL2_image / SDL2_ttf / SDL2_mixer を使う自作テスト | PNG の表示、文字描画、WAV の再生データを確認 |

絵と音の確認は、アプリ内のサーバ部分 (`DisplayServer`) を PC 上で動かし、届いたフレームを
画像に保存して目視したもの。Android 上のゲーム画面 (`GameActivity`) の表示・音の再生・
タッチ操作は実機で未確認。

## glibc について

- 同梱しているのは libc, libm, libpthread, libdl, librt, libresolv, libgcc_s, libstdc++ など。
  対応 CPU は arm64-v8a / armeabi-v7a / x86_64 / x86。
- glibc 本体は Termux プロジェクトの配布物 (termux-pacman の `glibc` パッケージ、2.44) を使う。
  Android のアプリのプロセスでは一部のシステムコール (clone3、rseq、set_robust_list など) が
  禁止されていて、普通の glibc はそれを呼んで強制終了させられる。Termux 版はそれらを呼ばない。
- **root が無くても動く。** その場合はアプリの `lib/` に入れたローダ (`libbrld.so`) で起動し、
  禁止されたシステムコールで終了させられる代わりに「未対応」を返す補助ライブラリ
  (`native/brshim.c`) を先に読み込ませる。プログラムが自分で SIGSYS の処理を登録しても (Wine など)、
  この補助ライブラリの処理は外さず、登録された処理は覚えておいて、seccomp 以外の理由の SIGSYS だけを渡す。
  Box64 で動かすとき (環境変数 `BR_DROP_EXEC=1`) は、アプリのフォルダのファイルを「実行できる形」で
  メモリに読み込むのを Android (SELinux) に拒否されたら、その印 (PROT_EXEC) を外してやり直す
  (Box64 は x86 の命令を変換して動かすので不要。Wine が Windows の DLL を読み込むときに必要になる。
  Termux 版の glibc の mprotect が拒否されたときに走らせる独自の処理は落ちることがあるので、通らない)。
  それでも Android の制限に触れるプログラムは動かない。
- root のシェルがアプリの作業領域に入れない端末では、自動で root を使わないシェルに切り替える。
- Android には `/etc/resolv.conf` が無いので、glibc 用プログラムはホスト名を解決できない
  (IP アドレス直指定の通信はできる)。`/etc/passwd` やロケールデータも無い。
- Wine (「追加機能」から入れたときだけ) は LGPL-2.1 以降。Debian 13 の `wine` 10.0~repack-6 のパッケージを
  そのまま使い、アプリが書き換えるのは `ntdll.so` と `wineserver64` の連絡用フォルダの場所 1 か所ずつ。
- Box64 は MIT ライセンス (Copyright (c) 2020 ptitSeb)。全文は `assets/box64/arm64-v8a.zip` の
  `LICENSE-box64.txt` と、アプリの設定 → 個人設定 →「オープンソースのライセンス」にある。
- SDL2・SDL2_image・SDL2_mixer・SDL2_ttf は zlib ライセンス (SDL2_ttf に含まれる FreeType は
  FreeType License)。SDL 1.2 互換は Debian の `libsdl1.2debian` (sdl12-compat、zlib ライセンス)。
- libgcc / libstdc++ は Debian 13 (trixie) の公式パッケージ `libgcc-s1` `libstdc++6`
  (GPL-3.0 以降 + GCC Runtime Library Exception、ソースは Debian のソースパッケージ `gcc-14`)。
- glibc は LGPL-2.1 以降。使っている版と調整内容 (パッチ) のソースは
  https://github.com/termux-pacman/glibc-packages の `gpkg/glibc` にある。
  版は APK 内の `assets/glibc/VERSIONS.txt` に記録している。

## ビルド

```sh
echo "sdk.dir=/path/to/android-sdk" > local.properties
native/build-sdl.sh         # SDL2 一式をビルド (初回のみ。各 CPU 向けの GNU クロスコンパイラが必要)
native/build-shim.sh        # root なし実行用の補助ライブラリをビルド
./fetch-glibc.sh            # glibc 一式を Debian から取得して SDL2 と合わせる (初回のみ)
./fetch-qemu.sh             # CPU エミュレータ (QEMU) を Termux から取得 (初回のみ)
./fetch-clamav.sh           # ウイルス対策エンジン (ClamAV) を Termux から取得 (初回のみ)
./fetch-box64.sh            # x86_64 を速く動かす Box64 を Termux から取得 (任意。無ければ QEMU で動く)
./gradlew assembleRelease   # app/build/outputs/apk/release/app-release.apk
```

Java のライブラリには依存していない。
補助プログラム `ptyrun` (シェルを疑似端末の中で動かす) はビルド済みのものを
`app/src/main/jniLibs` に入れてある。`native/ptyrun.c` を変えたら
`ANDROID_NDK_HOME=... native/build.sh` で作り直す。mkexe の TCC も同じくビルド済みで、
作り直すときは `ANDROID_NDK_HOME=... native/build-tcc.sh` (GitHub Actions の build-mkexe でもできる)。X11 用の PRoot (`libproot.so`・`libproot-loader.so`)
も同じくビルド済みで、作り直すときは `ANDROID_NDK_HOME=... native/build-proot.sh`。署名は同梱の `bionicrunner.keystore`
(自前配布用の固定鍵・パスワードは `app/build.gradle` に記載) で行うので、
再ビルドしても上書き更新できる。Play ストア等で公開する場合は非公開の鍵に差し替えること。
